# Отношения (Relationship)

Бот помнит, как к нему относится собеседник, и это попадает в промпт
отдельным state-слоем — в виде словесной инструкции о тоне общения,
**без чисел и прогресса**. Число уровня — внутреннее представление.

## Как это устроено

Три звена (write-path → store → read-path):

1. **`core/relationship/evaluator.py`** — раз в N сообщений собеседника
   спрашивает LLM: «как изменилось отношение, от -3 до +3?» (низкая
   температура, один вызов). Оцениваются ТОЛЬКО сообщения, адресованные
   боту (первый токен начинается с имени бота) — в отличие от
   `FactsExtractor`, который читает весь чат.
2. **`core/relationship/store.py`** — таблица `relationship` на той же
   SQLite (тот же `conn`, что у памяти). Применяет дельту к уровню:
   `progress += delta * 10` (шкала задокументирована ниже), при переходе
   уровня прогресс сбрасывается. Пишет строку в `relationship_log`.
3. **`core/relationship/relationship_provider.py`** — read-path:
   `render(addressee_nick)` возвращает словесную инструкцию по тону
   (реализует `StateProvider` из `core/layers.py`). При нейтральном
   уровне (6) — `None`: ничего не добавляем, модель и так так себя
   ведёт по умолчанию.

`CompositeStateProvider` (`core/state/composite_state_provider.py`)
объединяет несколько state-провайдеров: расписание + отношения.
Каждый провайдер тестируется отдельно (юнит) и вместе (интеграция) —
см. `tests/test_composite_state_provider.py`.

## Шкала уровней

`core/relationship/levels.py` — единственное место описания уровней:

| level | name              | инструкция в промпте                        |
|-------|-------------------|---------------------------------------------|
| 0     | Любовь            | очень тепло, симпатия                       |
| 1     | Влюблённость      | очень тепло                                 |
| 2     | Влечение          | очень тепло                                 |
| 3     | Дружба            | дружелюбно                                  |
| 4     | Привязанность     | дружелюбно                                  |
| 5     | Приветливость     | скорее позитивно                            |
| 6     | Нейтральность     | — (дефолт, ничего не добавляем)             |
| 7     | Неприязнь         | прохладно, колко                            |
| 8     | Вражда            | враждебно, резко                            |
| 9     | Ненависть         | враждебно, резко                            |

Инструкции намеренно без числовых значений — модель не должна знать
про «уровень 8» и прогресс.

## Алгоритм `apply_delta`

Простое и задокументированное решение:

```
new_progress = progress + delta * 10
if new_progress >= LEVEL_PROGRESS_CAP (100):
    if level == 0:            # верхняя граница — держим
        progress = 100
    else:
        level -= 1; progress = 0
elif new_progress < 0:
    if level == 9:            # нижняя граница — держим
        progress = 0
    else:
        level += 1; progress = 100
else:
    progress = new_progress
```

Отсюда практическое следствие: с нейтрального уровня (6, прогресс 0)
одно негативное сообщение-оценка (delta < 0) сразу опускает на 7,
а позитив сначала копится в прогресс и поднимает уровень только через
несколько оценок (на +3 каждый раз — ~40 тёплых сообщений).

## Конфиг `config/relationship.yaml`

```yaml
eval_every_n_messages: 10   # оценивать раз в N сообщений
delta_min: -3               # границы дельты, возвращаемой LLM
delta_max: 3
```

Дельту LLM жёстко зажимают в `[delta_min, delta_max]` — модель не может
случайно улететь на ±99.

## Фолбэки

- Невалидный JSON от LLM → `(0, "parse_error")`: отношения не должны
  портиться из-за сбоя парсинга.
- Ошибка LLM (сеть, 404 и т.п.) → `(0, "llm_error")`.
- Нет сообщений, адресованных боту → оценка не запускается вообще.

## Хранение

- `relationship(username PK, level, progress, updated_at)`.
- `relationship_log(id, username, delta, reason, created_at)` — аудит:
  почему изменилось (используется в ручных смоуках).
- Счётчик сообщений в `RelationshipEvaluator` — in-memory
  (`{username: count}`), не персистентный. После рестарта бот просто
  «досчитает» с нуля — осознанное упрощение.

## Тесты

- `tests/test_relationship_store.py` — создание нейтральной записи,
  накопление прогресса, переходы уровней в обе стороны, границы (0 и 9),
  запись в лог.
- `tests/test_relationship_evaluator.py` — порог срабатывания, сброс
  счётчика, клампинг дельты, фолбэки, фильтр «только боту».
- `tests/test_relationship_provider.py` — инструкции по уровням, никаких
  чисел в промпте, нейтраль = `None`.
- `tests/test_composite_state_provider.py` — расписание и отношения
  работают порознь и вместе; при нейтральном уровне инструкции нет.

Живые смоуки (критерии приёмки) прогонялись через `run_once` с общим
`runtime` (тот же путь, что у `--repl`): 10+ грубых → уровень 7
(Неприязнь); ~40 тёплых → уровень 5 (Приветливость); смешанные →
остаётся на уровне Нейтральности.
