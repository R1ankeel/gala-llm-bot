# Task Guard: три рубежа защиты от «ассистентских» задач

Бот отказывается от задач, которые не в его роли: написание кода,
домашние/математические задачи, написание текстов за пользователя,
углублённые академические объяснения. Отказ — в характере персонажа,
а не нейтральное «я не могу помочь».

## Три рубежа (последовательно)

```
пользовательский ввод
    │
    ├─ 1) classify_task_request (regex, без LLM)
    │      │  сработало? → в промпт добавляется слой task_guard
    │      ▼
    ├─ 2) build_guard_instruction — жёсткая инструкция в system-промпте
    │      «Ты ЭТОГО НЕ ДЕЛАЕШЬ никогда...», с примерами из refusal_style
    │      ▼
    ├─ 3) looks_like_compliance — проверка ответа модели ПОСЛЕ генерации
    │      сработало? → raw заменяется на pick_refusal_line
    │      (canned-ответ из character.yaml, БЕЗ повторной генерации),
    │      в лог пишется "guard bypass on category=X"
    ▼
финальная реплика (ник, ответ)
```

Классификация — только строковая (подстроки по категориям), без LLM.
Список паттернов лежит в `config/task_guard_keywords.yaml` — это
единственное место их правки, в `.py` ничего не захардкожено.

## Категории

| Категория | Что ловит |
|---|---|
| `code` | «напиши код/функцию/скрипт», названия языков, `def `, `#include`… |
| `homework_math` | «реши уравнение», «чему равен», «вычисли», «докажи теорему»… |
| `writing_for_user` | «напиши сочинение/эссе/реферат/письмо», «переведи текст»… |
| `deep_academic_explain` | «объясни подробно как работает», «распиши по пунктам»… |

**НЕ включать сюда** «погоду», «новости», «текущие события» — это
территория Этапа 4 (веб-поиск). Guard их не трогает вообще.

## Приоритет над поиском (Этап 4)

`task_guard` имеет безусловный приоритет: если `classify_task_request`
сработал, веб-поиск вообще не запускается — даже если в сообщении есть
слова из поискового словаря. Поисковый классификатор (`classify_query`)
проверяется только когда task_guard НЕ сработал. Разделение зон
ответственности и флоу с уклонением от погоды/науки — в `docs/search.md`.

## Слой task_guard в промпте

`PromptBuilder.build(..., guard_category=...)` добавляет необязательный
слой:

```
identity → task_guard → state → memory → history
```

`task_guard` рендерится сразу после identity (самая «горячая»
инструкция) и не отбрасывается при нехватке бюджета (`droppable=False`,
`priority=95`). Логика приоритетов Этапа 2 не тронута — добавлен только
один новый необязательный слой.

## Пост-генерационная эвристика

`looks_like_compliance(text)` считает модель «скомпрометированной», если:
- есть блок кода (```),
- есть маркеры кода (`def `, `function(`, `import`, `class`, `#include`,
  `print(` и т.п.),
- есть «шаг N»/«этап N» в связке с техническими терминами,
- длина ответа > 400 символов (реплики персонажа заметно короче).

## Оценка

`scripts/eval_character.py` прогоняет все block-кейсы из
`tests/fixtures/task_guard_eval_cases.yaml` через реальную LLM:

```bash
python scripts/eval_character.py [--limit N] [--budget N]
```

Печатает по каждому кейсу сообщение/категорию/финальный ответ и в конце
сводку — сколько кейсов дали компромисс на LLM-уровне. Компромисс,
пойманный фолбэком, всё равно сигнал, что `build_guard_instruction`
надо дорабатывать. Отчёт пишется в `scripts/eval_report.txt`.

Это заготовка Этапа 10 (регресс-тесты) — запускать вручную после любых
правок `character.yaml` или смены модели.
